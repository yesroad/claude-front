# Test Unit

순수 로직만 테스트한다. 시나리오를 먼저 합의하고 코드를 쓴다 - 어떤 경우를 덮을지 고르는 것이 사람의 판단이다.

## Workflow

1. 대상 확인. `$ARGUMENTS`(파일 또는 기능)를 읽는다. 없으면 `git status --porcelain`으로 방금 바뀐 파일에서 고른다. 아래 "대상"에 없고 화면으로 확인 가능한 것이면 테스트하지 않는 편이 낫다고 한 줄로 알리고 종료한다.
2. 시나리오 도출. Given-When-Then 목록을 만들어 먼저 보여주고 합의를 받는다. 경계값(0, 1, 최댓값, 빈값, 공백)과 "일어나면 안 되는 것"을 함께 낸다. 합의 전에는 코드를 쓰지 않는다.
3. 작성. 합의된 시나리오만 `<대상>.test.ts(x)`에 쓴다. 테스트 파일의 형식과 단언 규칙은 `.claude/rules/testing.md`가 자동으로 로드된다.
4. 실행. `vitest --run <파일>`(패키지 매니저는 lock 파일로 판별). 실패하면 출력을 그대로 보여준다. 테스트를 통과시키려고 구현을 바꾸지 않는다 - 같은 실패가 2회 반복되면 멈추고 무엇이 진짜 결함인지 사람에게 넘긴다.
5. 마무리. 덮은 것과 덮지 않은 것을 각각 한 줄로 알린다. 안 덮은 이유가 "화면으로 확인 가능"이면 그렇게 적는다.

## 대상 - 눈으로 확인 못 하는 것부터

1. 검증 - 규칙별 경계값. 빈값이 required 외 규칙을 통과하는지.
2. 변환 - 입력 → 출력 매핑, 순서 유지, 숨김 필드 제외.
3. 정렬과 페이지 - 정렬 기준, 페이지 분할, 마지막 페이지, 범위 밖 클램프.
4. 정책 계산 - 날짜, 금액, 상태 전이. 정책 값을 바꾸면 깨지는 테스트 1건을 둔다 - 변경을 알아차리는 장치다.
5. 데이터 정합성 - 참조 키가 전부 존재하는지, 열거형 값이 정의 안에 있는지. 데이터가 늘 때 회귀를 잡는다.

렌더만 하는 컴포넌트, 스타일, 레이아웃은 대상이 아니다. Provider 가 필요한 훅과 컴포넌트는 `/test-integration`.

## 작업 원칙

- 커버리지 숫자를 목표로 삼지 않는다. 덮이지 않은 핵심 로직이 있는지만 본다.
- 시나리오가 5개를 넘으면 무엇을 뺄지 함께 제안한다 - 테스트는 안전망이지 산출물이 아니다.
- `/commit`의 테스트 게이트는 이 스킬을 부르지 않는다. 게이트는 실행만 한다 - 커밋 직전에 테스트를 새로 쓰기 시작하면 그 커밋이 두 가지 일을 하게 된다.
