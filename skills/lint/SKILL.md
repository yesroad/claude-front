# Lint

`/check` 게이트에서, 또는 사람이 직접 불러 타입과 린트 오류를 정리한다. 컴파일러와 린터가 판정한 오류만 다루고, 수정은 동작과 타입 구조를 바꾸지 않는 국소 수정에 한한다. 타입 설계나 동작을 바꿔야 풀리는 오류는 설계 판단이라 고치지 않고 남긴다 - code-reviewer 와 사람 몫이다.

## Workflow

1. 명령 판별. lock 파일로 패키지 매니저를 정한다 - `pnpm-lock.yaml` → pnpm, `yarn.lock` → yarn, `bun.lock` → bun, 그 외 npm. `package.json`의 scripts 에서 린트는 `lint`, 타입 검사는 `typecheck`가 있으면 그것, 없고 `build`가 `tsc`를 포함하면 `build`, 둘 다 없으면 `tsc --noEmit`(프로젝트 참조가 있으면 `tsc -b --noEmit`).
2. 검사. 린트와 타입 검사를 둘 다 돌린다 - 린트만 통과했다고 하지 않는다.
3. 분류.
   - 간단 - `prefer-const`, 사용처 없는 `no-unused-vars`, import 정렬, 추론이 명확한 반환 타입 누락.
   - 복잡 - `TS2322`, `TS2345`, `TS2339` 같은 타입 불일치. 타입 정의를 먼저 읽고 근본 원인을 찾는다. 원인이 분명하고 한 파일 안의 국소 수정(잘못된 import, 빠진 좁히기, 틀린 인자)으로 끝나면 고친다. 타입 구조나 동작을 바꿔야 하면 고치지 않고 남긴다.
4. 수정. 하나씩 고치고 그 파일을 다시 검사한다 - 여러 오류를 한 번에 고치면 무엇이 무엇을 고쳤는지 알 수 없다. 우선순위는 타입 오류(컴파일 차단) → 린트 error → 린트 warning.
5. 전체 재검사 후 보고.

## 금지

- `any`, `@ts-ignore`, `@ts-expect-error`, `eslint-disable`로 우회하지 않는다 - 타입 오류는 대개 실제 결함의 신호다. 우회 없이 못 고치는 오류는 수정하지 말고 사유와 함께 보고한다.
- 로직을 바꾸지 않는다. 오류를 없애려고 동작을 바꾸는 것은 이 스킬의 일이 아니다.
- 같은 오류가 2회 수정 후에도 남으면 멈추고 사용자에게 넘긴다. 반복 시도하지 않는다.

## 출력 형식

```
수정 완료. 파일 <목록> / 해결 N개 (간단 N, 복잡 N)
남은 오류. 타입 N, 린트 N
복잡 분류 수정. <파일:줄> - <무엇을 왜 고쳤나>
최종. 전체 통과 | 오류 N개 남음
```
